Cross-session messaging between two separate top-level opencode sessions (siblings, not parent/child subagents; that path is the `message` tool). The sessions share a machine and a durable SQLite database. Both must opt in through an `invite` / `accept` token handshake. Gated by the `experimentalS2S` runtime flag.

Peers are addressed by their globally-unique session_id (the `ses_...` id), NOT by slug — session slugs are not unique. The `accept` output tells you the peer's session_id to use with `msg`/`leave`.

Usage:
1. On the inviter session, run `s2s(command:"invite")` to mint a one-shot token. Share that token out-of-band with the peer (chat, paste, etc.).
2. On the joining session, run `s2s(command:"accept", token:"<the-token>")` within 10 minutes. This writes the durable allow row in both directions (the consent record). The output reports the peer's session_id.
3. Either side can run `s2s(command:"list")` to check paired peers before sending.
4. Either side can run `s2s(command:"msg", target:"<peer-session-id>", body:"...")` for one peer, or `s2s(command:"msg", targets:["<peer-id-1>","<peer-id-2>"], body:"...", deliver_at:"2026-10-01T12:00:00Z", stagger_ms:1000)` for a batch. Each accepted target, including a same-process peer, gets a durable `s2s_message` row. A send result means stored, not delivered. The recipient commits its transcript message, each part, and the delivered mark in order. A receipt means the transcript was persisted; a hand-over race can repeat a live event, but it does not create another transcript row.
5. Either side can revoke with `s2s(command:"leave", target:"<peer-session-id>")`.

Commands:
- `invite`                   — mint a token bound to this session.
- `accept <token>`           — consume a peer's token; writes both allow directions.
- `msg <session-id|targets> <body>` — send to one peer or a bounded list of peers (addressed by session_id).
- `sent [session-id]`        — list your most recent sends, optionally filtered by recipient, with id, send time, and delivery state.
- `list`                     — list paired peers with session_id, title, consent direction, and `running` or `unknown` activity.
- `leave <session-id>`       — revoke the allow for a peer.
- `relay`                    — emit a capsule as a copy-pasteable JSON blob (zero-infra fallback for future cross-machine delivery).

Usage notes:
- Install the current build and restart each process. Startup applies the additive database migration automatically; there is no manual migration, readiness step, or extra environment variable. During a brief overlap, an old process cannot read new `s2s_message` rows. Mail for its session stays pending until a current process runs that session and drains it.
- No current presence row, or a stale row, means `unknown`: the send is accepted and remains pending until the recipient runs a current build. A fresh lower-capability row refuses the send: `Recipient is running an incompatible S2S build (capability <version>); upgrade it and retry.` A current presence row means a compatible process is live, not that the recipient has read the message.
- Old binaries may still write `s2s_inbox`; a new owner adopts each legacy row once. Old-binary delivery cannot acquire a retroactive atomic receipt, and messages already deleted before upgrade have no recoverable sent history. When checking an old binary against the migrated schema, use a database copy. That compatibility probe is not a runtime activation gate or a rollback procedure.
- The token TTL is 10 minutes; a token used after that is rejected.
- `msg` has a durable recipient pending-row cap of 50 and a soft, process-local sender throttle of 50 per UTC clock hour. Both apply to local and cross-process sends. The sender throttle resets on restart; it is not a security boundary. Every `msg` result reports used, limit, remaining, and the UTC reset time.
- `running` means a current-build process is live and serving that session, not proof of which process owns it; a run lease alone is not enough.
- Retries are safe: an identical resend to the same recipient within 10 minutes is deduped at insert and reported as already sent (with the original message id); nothing reaches the recipient twice.
- `msg` accepts `expires_at` as a timezone-qualified ISO instant. If expiry wins before the recipient starts the transcript, the instruction is withheld and the recipient sees one expiration summary for that drain batch. A started transcript completes even if the deadline passes mid-delivery.
- `msg` accepts exactly one of `target` or `targets` (1–20 peers). Optional `deliver_at` is a timezone-qualified ISO instant; with `targets`, `stagger_ms` offsets each target in order. Delivery is discovered from durable rows, not a sender-side timer. Expiry must fall after that target's due time. A batch reports an id, due time, or failure for each peer; one peer's refusal does not undo another's accepted send.
- `msg` accepts `supersedes` with the id of an earlier send from the same session to the same recipient. A still-pending instruction is retracted; the newer frame names the retracted id. If the older frame has started or finished delivery, the send still succeeds but explicitly reports `in_delivery` or `already_delivered` instead of claiming a retraction.
- Body length is capped at 16000 characters; longer bodies are rejected before delivery.
- Consent is checked against the durable s2s_allow table (session_id based): you can only `msg` a peer you have invited+accepted. An un-consented target is rejected with a clear error. This works the same whether the peer is in this process or another, and survives a restart.
- A one-directional consent entry is anomalous; a normal invite/accept pair has both directions.
- This tool is the cross-process sibling primitive. For parent/child subagent messaging, use `message` instead.
